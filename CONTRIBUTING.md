# Contributing to arr-mcp-server

Thanks for considering a contribution! This document covers the development setup, code conventions, and the workflow for adding new tools.

## Development setup

```bash
git clone https://github.com/alexscdt/arr-mcp-server.git
cd arr-mcp-server
npm install
cp .env.example .env   # fill in credentials for your own stack
npm run dev            # runs src/index.ts with hot reload (tsx watch)
```

Useful scripts:

| Command | What it does |
| --- | --- |
| `npm run dev` | Run the server with hot reload |
| `npm run typecheck` | TypeScript type checking (no emit) |
| `npm test` | Run the Vitest suite once |
| `npm run test:watch` | Run Vitest in watch mode |
| `npm run build` | Compile to `dist/` (uses `tsconfig.build.json` + postbuild script) |

You can smoke-test the running server with any MCP client, or simply ask it to call the `ping` tool.

## Code conventions

- **Strict TypeScript** — the project compiles with `strict` mode and `npm run typecheck` must pass with zero errors. Avoid `any`; prefer explicit types on exported functions.
- **Zod for runtime validation** — every external boundary (env config, tool inputs) is validated with a Zod schema. Tool handlers receive `unknown` and must `parse()` before using the input.
- **Clients / tools separation**:
  - `src/clients/` — one file per external service (Radarr, Sonarr, qBittorrent, Plex). Clients own HTTP calls, auth, and response typing. No formatting or MCP concerns here.
  - `src/tools/` — one file per MCP tool. Tools own input schemas, orchestration across clients, and human-readable output formatting. No raw HTTP here.
- Tool handlers return a plain `string`; errors are surfaced by the central handler in `src/index.ts`.

## Adding a new tool

1. **Client method** — add the API call(s) you need to the relevant client in `src/clients/` (or create a new client for a new service, following `src/clients/base.ts`).
2. **Tool file** — create `src/tools/<tool_name>.ts` exporting:
   - `<toolName>ToolDefinition: Tool` — the MCP tool definition (name, description, JSON `inputSchema`);
   - a Zod input schema mirroring the `inputSchema`;
   - `handle<ToolName>(args: unknown): Promise<string>` — parses the input and returns formatted text.
3. **Register it** — add the definition + handler pair to `toolRegistry` in `src/tools/registry.ts`.
4. **Test it** — add `tests/tools/<tool_name>.test.ts` covering input validation and output formatting (see existing tests for the pattern).
5. **Document it** — add a section for the tool under "Available tools" in `README.md` (params table + example prompt).

## Running tests

```bash
npm test
```

Tests live in `tests/` and use [Vitest](https://vitest.dev/). Test schemas, formatters, and pure functions directly; when a handler talks to a client, stub the client methods with `vi.spyOn(client, 'method').mockResolvedValue(...)` (see `tests/tools/add_movie.test.ts` and `tests/tools/list_downloads.test.ts` for examples). Don't hit real services from tests.

## Pull request checklist

Before opening a PR, make sure:

- [ ] `npm run typecheck` passes
- [ ] `npm test` passes
- [ ] `npm run build` succeeds
- [ ] README updated if you added or changed a tool or an environment variable
- [ ] **Do not edit `CHANGELOG.md` manually** — it is generated by [release-please](https://github.com/googleapis/release-please) from commit messages

## Commit messages

This repo uses **[Conventional Commits](https://www.conventionalcommits.org/)**, and this is not just a style preference: release-please derives version bumps and the changelog from commit messages.

- `feat: …` → minor version bump
- `fix: …` → patch version bump
- `feat!: …` or a `BREAKING CHANGE:` footer → major version bump
- `docs:`, `chore:`, `ci:`, `test:`, `refactor:` → no release

Example: `feat: add overseerr request tool`
